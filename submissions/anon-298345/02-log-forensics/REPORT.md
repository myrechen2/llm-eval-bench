# 2026-03-14 支付重复扣款与网关 502 事故复盘报告

## 1. 根因分析

本次重复扣款由 **payment-svc `v2.14.0`（`DEP-7731`）的超时重试逻辑缺陷**与 **PayNova 渠道延迟升高**共同触发：

1. **直接根因（机制）**：`payment-svc v2.14.0` 移除了原有的状态轮询（`status_check`），改为在调用 PayNova 发生客户端超时（3000 ms）后直接发起重试（最多 3 次）。但重试请求没有复用原请求的 `idempotency_key`，而是每次重试都生成了全新的 `idem_key`。PayNova 在服务端耗时超过 3000 ms 时仍会继续处理并完成先前的扣款请求；由于新旧请求携带不同幂等键，PayNova 将其视为独立交易并多次扣款。
2. **为什么之前/之后的版本没有问题**：
   - 回滚前的 `v2.13.4`（及回滚后的 `DEP-7740`）在超时后通过 `status_check` 查询状态，不会盲目重新扣款；
   - 后续修复版本 `v2.14.2`（`DEP-7752`）虽保留重试，但改为复用同一支付意图的 `idempotency_key`，利用 PayNova 幂等保证避免重复创建 charge。
3. **网关 502 放大效应**：当多次尝试与退避总耗时超过 gateway 的 `proxy_read_timeout`（8 s）时，nginx 返回 `502`，但后端 `order-svc` 与 `payment-svc` 仍在继续执行后续重试并完成扣款。

## 2. 关键证据

1. **首笔事故重复扣款（`O0314-003221`）**：
   - `payment-svc.log`：`2026-03-14T06:40:42.501Z` `attempt=1 idem_key=pi_e63defb623db13bac408 result=timeout duration_ms=3000`；随后 `06:40:42.766Z` 发起 `attempt=2`，但使用了新键 `idem_key=pi_220fcea2cd9e0cdda14d` 并于 `06:40:44.812Z` 返回 `succeeded`（`charge_id=ch_f3c69d1fae2b8a3a`）。
   - `provider_charges.csv`：同一订单 `O0314-003221`（应付 `14950` 分）存在两笔 `succeeded` 扣款：`ch_9dd7d5c265b7ebfa`（`06:40:43Z`）和 `ch_f3c69d1fae2b8a3a`（`06:40:44Z`）。
2. **跨窗边界证据（`O0314-004083`）**：
   - `2026-03-14T08:02:25.040Z` 发起 `attempt=1`（`pi_6c0487855386227e0c99`）超时后，`v2.14.0` 于 `08:02:28.260Z` 发起不同 `idem_key` 的 `attempt=2`，产生最后一笔额外扣款 `ch_81339d0ce7080870`（`08:02:30Z`），此后随着 `DEP-7740` 完成回滚，重复扣款立即停止。
3. **指标对比**：
   - `payment-svc` `charge.result` p95 延迟从发布前 2 小时窗口的 `2456 ms` 升至故障窗口的 `3000 ms`（客户端超时上限），超时率达 `31.9%`（`400 / 1254`）；
   - 故障窗口内 gateway `POST /api/v2/checkout` 共产生 `88` 次 `502`。

## 4. 排除的误导线索

- **Gateway keepalive 变更（`DEP-7729`）**：仅调整客户端侧 `keepalive_timeout`（65s→30s），不影响上游超时，且错误日志均为上游读取超时。
- **礼品卡+银行卡组合支付（split payments）**：虽会生成两笔不同键的 charge（`_gc` 与 `_card`），但两者之和等于订单金额，不产生 extra charge 或待退金额。
- **`order-svc v3.9.0`（`DEP-7735`）**：开始发布于 `07:08Z`，晚于首笔事故重复扣款（`06:40:44Z`），与本次故障无关。
- **PayNova 延迟升高本身**：延迟是诱因（触发 3000 ms 超时），而非重复扣款根因；若正确复用幂等键或轮询状态，不会导致多扣。

## 5. 修复与预防建议

1. **强制幂等键绑定支付意图**：同一订单/支付意图的重试必须复用同一个 `idempotency_key`，禁止在重试循环中重新生成。
2. **超时预算对齐**：`payment-svc` 单次超时 × 最大重试次数 + 退避时间应严格小于 gateway `proxy_read_timeout`（8 s），或在网关超时时配合异步状态查询。
3. **自动对账与告警**：对 `provider_charges` 与 `orders` 建立分钟级核对告警，一旦出现 `succeeded_sum > owed` 或超时率突增立即触发告警并熔断自动重试。
